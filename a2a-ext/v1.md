## 1. Abstract

This extension adds **bounded human authorisation** to A2A task execution. It
allows an agent to classify a requested action by its reversibility, to require
a recorded sanction from one or more named human stewards before the action
takes effect, and to emit a tamper-evident receipt of every gate crossing —
admissions and refusals alike.

The extension is a **profile extension** with a **state machine** component. It
adds no RPC methods, defines no new task states, and modifies no core data
structure. All extension data is carried in the `metadata` maps of existing
objects and in `DataPart` payloads, in conformance with the limitations in the
A2A extensions documentation.

## 2. Motivation

A2A answers *which agent can perform this task*. It does not answer *whether a
human accepted responsibility for the consequences*, and it provides no
protocol-native way to express that a task is waiting on that acceptance,
which human it is waiting on, or what was decided.

This gap is not incidental to A2A. A recent gap analysis of five agent
interoperability protocols — MCP, A2A, ACP, ANP and ERC-8004 — against a
six-dimension governance taxonomy found human escalation, dissent preservation
and voting absent from all five, and concluded that agent community governance
constitutes a missing architectural layer above the interoperability standards
rather than a missing feature inside them.<sup>[1]</sup>

This extension does not attempt that layer. It addresses **one** dimension —
human escalation — and contributes partially to two others — dissent
preservation and audit. Membership, deliberation and preference aggregation
are explicitly out of scope.

**Why the core protocol is insufficient.** Three properties are required and
none is expressible in core A2A:

1. A task may need to *stop and wait for a specific named person*, with the
   reason, the class of action, and the identity of the awaited steward
   legible to the client. `AUTH_REQUIRED` signals that authorisation is
   needed; it carries no structure describing whose, for what, or under which
   policy.
2. A record of the decision must survive the task. A2A task state is
   operational and terminal states are coarse: `COMPLETED`, `FAILED`,
   `CANCELED`, `REJECTED`. A refusal by a human steward, its reason, and the
   conditions under which the proposal may be reopened are not distinguishable
   from an agent-side rejection.
3. **Message integrity is not decision authenticity.** A correctly signed,
   hash-verified message can faithfully transmit a decision that was never
   made. Signed Agent Cards establish cryptographic authenticity and integrity
   for an agent's advertised identity and capabilities; the binding between
   that agent and the authorising human lies outside A2A semantics. This
   extension makes the kind of evidence behind a sanction an explicit,
   machine-readable field rather than an assumption.

Requirement 3 is derived from an observed failure rather than from a threat
model: in a two-node pilot, a capsule whose hash was independently verified
and matched exactly reported a steward decision that the steward had not made.
The message was cryptographically unimpeachable and substantively false.

## 3. Extension URI and versioning

The URI identifying this extension is:

```
https://mathr.ch/ext/sanction-gate/v1
```

Agents supporting this extension MUST use this URI exactly. Any breaking change
to the data structures, parameters or flows defined here MUST be issued under a
new URI. Clients requesting a version an agent does not support MUST have the
activation request ignored; agents MUST NOT fall back to a different version.

All metadata keys defined by this extension are prefixed with the extension
URI followed by `/`.

## 4. Agent Card declaration

Agents supporting this extension MUST advertise it as an `AgentExtension`
object within `capabilities.extensions`.

Agents that gate any action behind human sanction SHOULD declare
`required: true`. Gating changes how requests are processed and is fundamental
to the agent's security posture; a client unaware of the extension would
misread `AUTH_REQUIRED` as a credential problem and retry.

`params` MUST conform to the following schema:

```json
{
  "type": "object",
  "title": "SanctionGateParameters",
  "properties": {
    "maxClass": {
      "type": "string",
      "enum": ["R0", "R1", "R2", "R3"],
      "description": "The highest reversibility class this agent will accept over A2A. Requests classified above it are refused."
    },
    "gatedClasses": {
      "type": "array",
      "items": { "type": "string", "enum": ["R1", "R2", "R3"] },
      "description": "Classes for which this agent requires human sanction."
    },
    "authenticityKinds": {
      "type": "array",
      "items": { "type": "string", "enum": ["cryptographic", "procedural"] },
      "description": "Kinds of authenticity evidence this agent produces for its own sanctions. 'asserted' MUST NOT be declared."
    },
    "separationAtR3": {
      "type": "boolean",
      "description": "Whether the agent enforces that at least one R3 steward is outside the beneficiary's reporting line."
    },
    "emergencyPath": {
      "type": "boolean",
      "description": "Whether a budgeted single-steward emergency path exists."
    },
    "receiptRetention": {
      "type": "string",
      "description": "ISO 8601 duration for which receipts remain retrievable."
    },
    "policyUri": {
      "type": "string",
      "format": "uri",
      "description": "Where the agent's classification rules are published."
    }
  },
  "required": ["maxClass", "gatedClasses", "authenticityKinds"]
}
```

Example declaration:

```json
{
  "capabilities": {
    "extensions": [
      {
        "uri": "https://mathr.ch/ext/sanction-gate/v1",
        "description": "Irreversible actions require recorded human sanction before taking effect.",
        "required": true,
        "params": {
          "maxClass": "R3",
          "gatedClasses": ["R2", "R3"],
          "authenticityKinds": ["procedural"],
          "separationAtR3": true,
          "emergencyPath": false,
          "receiptRetention": "P10Y",
          "policyUri": "https://example.org/gate-policy"
        }
      }
    ]
  }
}
```

## 5. Activation

Activation follows the standard mechanism. A client requests activation by
listing the extension URI in the `A2A-Extensions` request header, and the agent
echoes successfully activated extensions in the response header.

Where an agent declares this extension with `required: true` and a client does
not request activation, the agent MUST reject the request with
`ExtensionSupportRequiredError`.

## 6. Data structures

### 6.1 Gate annotation

An agent that has classified a request MUST annotate the task status message
metadata with a gate object under the key
`https://mathr.ch/ext/sanction-gate/v1/gate`:

```json
{
  "class": "R3",
  "classBasis": "rule:publish-external-v2",
  "classDefaulted": false,
  "requiredSanctions": 2,
  "collectedSanctions": 1,
  "awaiting": ["steward:ops-lead", "steward:external-reviewer"],
  "proposalHash": "sha256:...",
  "hashCanon": "sorted keys, compact JSON, UTF-8, excluding volatile fields",
  "effectNotBefore": "2026-09-20T14:00:00Z",
  "outcome": "pending",
  "receiptRef": "urn:sanction-receipt:..."
}
```

`class` MUST be one of `R0`, `R1`, `R2`, `R3`, defined by reversibility:
undoable unilaterally at negligible cost (`R0`); undoable unilaterally at
material cost or within a limited window (`R1`); undoable only with another
party's cooperation (`R2`); not undoable, or undoable only by affecting
non-consenting third parties (`R3`).

`classDefaulted` MUST be `true` where no classification rule matched. Where no
rule matches, `class` MUST be `R2`. An agent MUST NOT assign `R0` or `R1` by
default.

`outcome` MUST be one of `pending`, `admitted`, `refused`, `lapsed`, `open`.
`open` denotes a decision that was reported and subsequently withdrawn: it is
neither an admission nor a refusal, and recording it as either would falsify
the record.

### 6.2 Sanction receipt

A receipt MUST be emitted for every gate crossing, including refusals. It is
carried as a `DataPart` whose metadata declares the key
`https://mathr.ch/ext/sanction-gate/v1/receipt`.

```json
{
  "receiptId": "urn:sanction-receipt:8f3a...",
  "proposalHash": "sha256:...",
  "taskId": "...",
  "class": "R3",
  "classBasis": "rule:publish-external-v2",
  "downgrade": null,
  "outcome": "admitted",
  "sanctions": [
    {
      "steward": "steward:ops-lead",
      "authenticity": "procedural",
      "evidenceRef": "confirm:2026-09-19T09:14Z/voice",
      "signedAt": "2026-09-19T09:15:02Z",
      "relation": "different-reporting-line",
      "reservation": null,
      "validUntil": "2026-09-26T09:15:02Z"
    }
  ],
  "assembledAt": "2026-09-19T09:02:11Z",
  "dispatchedAt": "2026-09-19T09:02:14Z",
  "receivedAt": "2026-09-19T09:02:15Z",
  "effectAt": "2026-09-20T14:00:04Z",
  "supersedes": null,
  "prevReceipt": "urn:sanction-receipt:7c21..."
}
```

`authenticity` MUST be one of:

- `cryptographic` — a signature verifiable under a key bound to the named
  steward;
- `procedural` — confirmation obtained out of band through a channel the
  assembling agent does not control;
- `asserted` — a claim by the assembling agent, carrying no evidential weight.

A sanction whose `authenticity` is `asserted` MUST NOT admit an action of class
`R2` or above. Agents MUST NOT declare `asserted` in `authenticityKinds`.

`assembledAt`, `dispatchedAt` and `receivedAt` are three distinct facts and MUST
be recorded separately. An implementation that derives one from another cannot
distinguish a message that was prepared from one that arrived.

`prevReceipt` chains receipts. Receipts MUST be append-only. Content referenced
by a receipt MAY be erased on request; the receipt MUST retain the hash, class,
stewards and timestamps, so that an immutable record can coexist with a right
to erasure under the GDPR and the Swiss nLPD.

Receipts MUST NOT contain any aggregate rating, score, or ranking of any person
or agent.

## 7. Flows

The extension defines no new task states. It annotates the existing eight
operational states.

| Situation | Core state | Extension metadata |
|---|---|---|
| Classified, sanction required, waiting | `AUTH_REQUIRED` | `outcome: pending`, `awaiting: [...]` |
| Sanctions collected, R3 delay running | `WORKING` | `outcome: admitted`, `effectNotBefore` set |
| Admitted, executing | `WORKING` | `outcome: admitted` |
| Admitted and done | `COMPLETED` | receipt `DataPart` attached |
| Steward refused | `REJECTED` | `outcome: refused`, reason and reopen condition |
| Sanction window elapsed unused | `AUTH_REQUIRED` | `outcome: lapsed` |
| Reported decision withdrawn | `AUTH_REQUIRED` | `outcome: open`, `supersedes` set |
| Class above `maxClass` | `REJECTED` | `outcome: refused`, basis `class-exceeds-max` |

Normative flow requirements:

1. An agent MUST classify a request before any effect occurs, and MUST NOT
   allow an action of class `R1` or above to take effect before a receipt
   recording its sanction exists.
2. A sanction MUST bind to exactly one `proposalHash`. Any change to the
   proposal MUST invalidate every sanction already collected for it.
3. Absence of sanction MUST be treated as refusal. Agents MUST fail closed
   where stewards are unavailable.
4. Any participant MAY raise a task's class while the task is live. No
   participant may lower it.
5. A steward MAY sanction *with reservation*: the action proceeds and a signed
   objection is recorded in the receipt and MUST NOT be removed. Reservation is
   the dissent-preservation primitive of this extension. Agents implementing it
   SHOULD expose the aggregate reservation rate, since a sustained rate of zero
   indicates the channel is not usable rather than that no objections exist.
6. Agents MUST NOT select, rank or influence the assignment of stewards for
   proposals they themselves originate.

## 8. Dependencies

This extension has no required dependencies.

It has an **optional** dependency on any future extension providing
cryptographic binding between a human principal and a signature. Where such an
extension is present and active, implementations SHOULD produce `authenticity:
cryptographic` and SHOULD NOT rely on `procedural` evidence for class `R3`.

## 9. Conformance

- **Level 1 — Traced.** Receipts emitted for every gate crossing at class `R1`
  and above, refusals included.
- **Level 2 — Gated.** Level 1, plus classification with the `R2` default,
  signed downgrade, class-to-sanction mapping, sanction expiry, and separated
  integrity and authenticity evidence.
- **Level 3 — Separated.** Level 2, plus declared steward relations, structural
  separation at `R3`, the reservation channel, proposer/judge separation, and
  receipts verifiable by a party outside the operating organisation.

Implementations SHOULD declare their level in `params`. Independence weighting,
Sybil resistance across a federation, and cryptographic steward binding are
outside all three levels in this version.

## 10. Security considerations

This extension is **additive to** the agent's authentication and authorisation
controls and MUST NOT be used to bypass them. A sanction records that a human
accepted responsibility; it does not authenticate the caller, and an agent MUST
apply its ordinary security checks regardless of gate outcome.

All extension data arriving from an external party MUST be treated as untrusted
input and validated. In particular, an agent MUST NOT accept a counterparty's
assertion of its own `class` without applying its own classification rules;
`class` received from a peer is a claim, and ambiguity MUST resolve upward.

Where an emergency path exists, it MUST be budgeted: a finite, pre-declared
number of single-steward admissions per period, after which the path is closed
until the next period. Each use MUST require two post-hoc reviews before the
same steward may declare another emergency. Visibility alone does not restrain a
practice that works; scarcity does.

Receipts may contain personal data. Implementations MUST support erasure of
referenced content while retaining the receipt (§6.2).

## 11. Reference implementation

A reference implementation is planned as a Python package layered on
`a2a-python`, providing a server-side gate middleware and a client-side
receipt verifier, with a conformance test suite covering Levels 1 to 3. It is
not yet available. This specification is published ahead of it so that the
design can be attacked before it is built.
